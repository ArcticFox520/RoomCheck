# 工程决策记录（ENGINEERING_DECISIONS）

本文件记录《工作指导.md》第 43 节列出的工程细节及实现中必须明确、但不改变已冻结业务规则的选择。所有决策均可由测试或代码审查复核。

| # | 问题 | 决策 | 理由/影响 |
|---|---|---|---|
| 1 | 寝室编号前导零 | `room_number` 以字符串保存；当起止寝室号均为相同长度且以 `0` 开头时，按该宽度补零生成；比较/去重按数值规范化 | 避免 `0201` 与 `201` 被错误合并；API 返回规范化字符串 |
| 2 | 楼栋名称修改是否改变寝室唯一标识 | `room_key = building_name + "#" + room_number`；楼栋改名等同于全部寝室移出+新增 | 与“room_key 由楼栋名称和寝室编号构成”一致；旧备注/图片保留在库中，可在管理员“移出范围”区域查看和删除 |
| 3 | 组空位定义 | 被移出寝室原所在的 `(day_index, period)` 即一个空位 | 新增寝室优先随机填入这些空位；空位数量=被移出寝室数 |
| 4 | 无空位时如何处理已超出均衡目标的旧组 | 保留旧寝室，不移动；新增寝室每次选择当前寝室数最少的查寝日，再选该日寝室数最少的时段；并列随机 | 满足“保留寝室不重排”；新增量少时优先补轻载组 |
| 5 | 单楼层长楼栋范围 | 一个楼层长对应一个楼栋的连续起止寝室范围（对应 Config Agent 的单一 `building_name`） | 简化配置与 N 计算；多楼栋可由多个楼层长账户管理；如需多范围可后续扩展表结构 |
| 6 | 周计划数量 | 每个楼层长仅保留一个“当前”周计划；跨周不自动清理，直到手动重置 | 满足“跨周未查完保留，禁止自动清空”；重置时删除旧计划并创建新计划 |
| 7 | 重置时的“新周” | 重置生成当前自然周的新计划；同一周内多次重置会替换当前计划 | 与“开始新一周”语义一致；不产生历史归档 |
| 8 | 排班随机源 | `/dev/urandom` + xorshift 兜底；不保存随机种子 | 随机不可复现；排班结果、操作人、时间、数量写入审计 |
| 9 | 历史排班 | 不保留历史周计划（重置会删除旧周排班、勾选、备注、图片记录） | 工作指导未要求历史归档；删除账户时同样级联全部数据 |
| 10 | 数据库并发 | 单进程、单 SQLite 连接、FULLMUTEX + 全局递归互斥锁串行化写操作 | 业务规模小；避免多写连接竞态；备份/恢复期间可阻塞写入 |
| 11 | SQLite 链接方式 | 内置 SQLite 3.46.1 amalgamation，静态编译，`SQLITE_OMIT_LOAD_EXTENSION` | 单文件部署，无动态 SQLite 依赖 |
| 12 | musl 工具链 | amd64 使用 Debian `musl-gcc`；arm64 使用 musl.cc 交叉工具链或 arm64 Alpine 容器内 `gcc` | 产物均为 `-static -no-pie`，`file` 显示 statically linked，无 `INTERP`/`NEEDED` |
| 13 | 迁移/恢复快照 | 恢复前创建 `pre_restore_*` 快照；快照不计入“保留 3 份”备份，另保留最新 2 份 | 防止错误恢复造成不可逆损失；避免快照挤占正式备份 |
| 14 | 备份内容一致性 | 备份在全局 DB 锁内执行：`sqlite3_backup` 复制数据库，再复制图片目录；manifest 记录数据库 SHA-256 | 数据库与图片来自同一批次 |
| 15 | 恢复失败回滚 | 恢复前快照 + 恢复失败时覆盖回滚；恢复后删除全部 Session | 防部分恢复；强制重新登录 |
| 16 | 每日备份时间 | 每日 03:00（Asia/Shanghai）后检查；启动时补偿执行；失败 5 分钟后重试 | 满足每日备份；避免重启导致漏备 |
| 17 | 日志保留边界 | 周一 00:00（Asia/Shanghai）后清理 `created_at < 本周周一 00:00` 的日志；`meta` 记录最后清理周 | 日志最多保留一个自然周；边界明确、可重入 |
| 18 | 管理员与楼层长锁定计数 | `account.username_norm` 全局唯一；内存锁按规范化账户名计数 | 在全局唯一账户名前提下等价于按账户/角色分别计数；不写 SQLite |
| 19 | 图片与备注关联 | `note_image.note_id` 可空；上传支持可选 multipart `note_id`；前端普通图片为寝室级，不强制关联备注 | 满足“删除备注级联关联图片”；普通图库图片不因删除某条备注而误删 |
| 20 | 上传类型限制 | 在“扩展名/MIME 黑名单”之外，要求内容签名识别为图片或客户端 MIME 以 `image/` 开头；拒绝可执行/脚本/HTML/SVG/压缩包 | 工作指导要求至少两层黑名单；额外签名校验提升安全性，不改变黑名单机制 |
| 21 | 管理端日期筛选 | `/api/admin/overview?date=` 服务端按该日期统计账户进度；`/api/admin/accounts/:id/week` 返回整周数据，前端按日期筛选面板 | “按楼层长和日期筛选”在聚合层实现，详情层保留完整上下文 |
| 22 | 账户删除后的图片 | 到期清理先尝试删除图片文件，再条件删除账户行；文件删除失败则保留数据并重试 | 避免“数据库已删但文件残留”或“文件已删但记录仍在”的不可追踪状态 |
| 23 | 孤儿上传目录 | 后台启动/周期性清理：账户不存在或周计划不存在且无图片记录的目录 | 处理重置/永久删除中断留下的目录，保证记录与文件一致 |
| 24 | CSRF Token 轮换 | 修改密码后轮换当前 Session 的 CSRF Token；其他 Session 失效 | 降低 Token 泄露风险；前端更新响应中的新 Token |
| 25 | Cookie Secure | 默认关闭，通过 `ROOMCHECK_COOKIE_SECURE=1` 开启 | 容器只提供 HTTP，HTTPS 由外部代理终止；部署方可按需开启 |
| 26 | 管理员初始化密码 | `ADMIN_INIT_PASSWORD` 可指定；否则生成 14 位随机密码并仅打印一次 | 便于自动化部署，同时默认安全 |
| 27 | 管理员账户数量 | 不提供创建管理员 API；系统仅保留初始化管理员 | 满足“管理员是唯一管理入口”；避免越权创建 |
| 28 | 前端架构 | 原生 HTML/CSS/JS，hash 路由，无构建步骤；CSP 禁止内联脚本 | 降低交付复杂度；静态资源由同一 C 服务提供 |
| 29 | 图片访问 | `/api/images/:id/file` 同源 Cookie 校验，`Content-Disposition: inline`，`nosniff` | 防止未授权访问与 MIME 嗅探 |
| 30 | 数据库身份 | `account` 单表 + `role` 字段 + `username_norm` 唯一索引 | 用数据库直接保证管理员/楼层长账户名全局唯一 |
| 31 | 数据导出 | 不提供导出 UI | 按工作指导冻结项执行 |
| 32 | 时区 | 固定 UTC+8 时间计算，不依赖系统 tzdata | Asia/Shanghai 无夏令时；容器精简 |
| 33 | 静态资源缓存 | HTML `no-store`，CSS/JS 5 分钟缓存 | 更新及时且减少重复传输 |
| 34 | 备份失败处理 | 自动备份失败写 `backup_failed` 警告并在 5 分钟后重试；手动备份返回错误但同样记录警告 | 与“备份失败只写警告日志”一致，同时让管理员获知 |
| 35 | 日志写入失败 | 永久删除等关键操作在同一事务内写审计，失败则回滚；普通操作记录 stderr 警告 | 满足“关键日志未写入阻断关键操作” |
| 36 | DayPlan 实体 | 不单独建 DayPlan 表；`check_group.day_index` + `room_check.group_id/position` 表达每日/每组排班 | 与工作指导的每日分组语义等价，减少冗余表 |
| 37 | 管理员概览日期筛选 | `/api/admin/overview?date=` 由服务端按日期统计；详情页按 6 个查寝日面板筛选 | 同时支持“按楼层长”与“按日期”查看 |

以上决策不改变工作指导中已冻结的业务规则；如后续需要变更，应先更新业务规格，再调整实现与验收用例。
